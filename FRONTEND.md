# Frontend Guide

## Overview

StockLine Inventory is a browser-based inventory application built with React, TypeScript, TanStack Start, and TanStack Router. The frontend includes the dashboard, product and category management, stock operations, sales reports, account controls, and settings. It is designed to work without a remote application server: operational data is stored in the current browser using IndexedDB through Dexie. This makes the app convenient to preview and use locally, but it also means data does not automatically follow a user to another browser or device.

The interface combines a persistent navigation shell with route-level pages. React components own the interactive forms and views, while shared hooks provide live data and keep screens updated after IndexedDB changes. Tailwind CSS 4 supplies utility styling, Motion provides transitions, and Lucide React supplies interface icons.

## Application Structure

The frontend source is under `src/`. The root route and document shell are defined in `src/routes/__root.tsx`; route components live beside it in `src/routes/`. TanStack Router uses file-based routing, so each route file corresponds to a URL. `src/routeTree.gen.ts` is generated by the router tooling and should not be edited manually. `src/router.tsx` creates the router and its React Query client.

Reusable application-level components are in `src/components/`. `AppShell.tsx` provides navigation, the page header, theme control, mobile navigation, and sign-out. `LoginScreen.tsx` handles sign-in. `ItemForm.tsx` and `CategoryForm.tsx` contain the main editors, while `Modal.tsx` supplies dialogs, loading panels, field helpers, and empty states. The `components/ui/` directory contains reusable Radix UI primitives.

The `src/lib/` directory contains shared behavior. `db.ts` defines the Dexie database, data types, validation, and operations. `auth.tsx` exposes the current user and role through React context. `ledger.ts` provides hooks for categories, items, activity, and user-accessible data. `format.ts` centralizes display formatting, and `theme.tsx` manages the light and dark appearance. Keep page-specific presentation in route components, and put shared data or interface behavior in these existing modules when it will be used in multiple places.

## Main Screens

- `/` is the dashboard, summarizing stock, value, categories, low-stock items, and recent activity for the current user.
- `/items` provides searchable inventory, filters, item details, editing, stock adjustment, and history.
- `/categories` manages categories and their custom attributes, allowing different product types to have different fields.
- `/activity` shows recent inventory events and their available context.
- `/admin` contains requests, transfers, stocktaking, returns, purchasing, suppliers, thresholds, and notifications.
- `/reports` supports daily sales entry and history. Staff submit individual reports; enabled managers can review team sales and submit branch summaries; admins inspect submissions across branches.
- `/profit-loss` summarizes sales revenue, cost, and profit for authorized users.
- `/settings` provides account security, team administration, backup and restore, and workspace controls, including the admin manager-layer switch.

## Data, Authentication, and Access

The local database is declared in `src/lib/db.ts`. Dexie stores categories, items, users, activity, daily sales reports, and operational records such as transfers and purchase orders. Database schema changes use numbered Dexie versions so existing browser data can be upgraded. Use the database helpers instead of writing directly to tables from unrelated UI code; this keeps validation, history, and access checks near the operation they support.

Hooks in `ledger.ts` use Dexie live queries. A successful edit therefore updates subscribed views without requiring a page refresh. The same module filters categories, items, and activity according to the signed-in user and selected branch. Loading and empty states should be retained when adding new pages because browser database queries resolve asynchronously.

The authentication provider exposes the user, administrator status, selected branch, and manager-section setting. Navigation is assembled according to the active role. Staff are restricted to assigned branch data; managers receive team and operational views when the manager layer is enabled; administrators can manage the overall workspace. The manager setting is stored in IndexedDB and hides manager-only navigation and behavior when disabled. Existing user records are kept so an administrator can turn the feature back on later.

This is a frontend-only workspace, not a centrally hosted identity or data service. Browser-local accounts and access checks are useful for the current application model, but they should not be treated as server-enforced security for a multi-device production deployment. A shared production workspace would need an authenticated backend and authorization checks on the server as well as a data synchronization strategy.

## Visual System and Interaction

Global visual tokens and Tailwind theme mappings are defined in `src/styles.css`. The palette uses deep teal navigation, light neutral surfaces, green accents, and distinct amber and rose states, with corresponding dark-theme values. Typography is based on DM Sans. Shared utility classes such as `glass`, `label-mono`, and `card3d` help maintain consistent surfaces, labels, and hover behavior.

Use the theme tokens rather than introducing unrelated colors. Forms should use the shared `Field` helper and established button styles. Use Lucide icons for recognizable actions and accessible names for icon-only controls. Motion supports page entrance and selected list transitions; keep it subtle. Toasts, loading panels, and empty states communicate results and query status.

The shell adapts its navigation for smaller screens. Desktop uses a vertical sidebar; mobile uses a bottom navigation bar with an expandable list for additional destinations. Page layouts rely on responsive Tailwind breakpoints, flexible grids, and horizontally scrollable tables where required. When adding controls, test narrow widths as well as desktop so text, buttons, and tables do not overlap or become unreachable.

## Local Development

Install the project dependencies with `npm install`, then run `npm run dev` to start the Vite development server. `npm run build` creates a production build. `npm run lint` runs ESLint. The project uses TypeScript, so keep component props and stored record shapes typed, and update the database version when changing persisted schema.

For a new feature, identify its owning route or shared component. Keep data access in `db.ts` and reusable selectors in `ledger.ts`; use live queries for views that should respond to edits. Preserve role checks and provide loading, empty, success, and error states. Run build and lint checks, then inspect desktop and mobile layouts.
